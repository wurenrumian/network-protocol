# 自定义协议设计 · protocol

本文件是设计方法论的主文档：从「问题定义」出发，逐层给出 wire format 范式、核心机制、设计取舍、不变量与边界条件。三个成熟协议（Redis RESP、MySQL 协议、Kafka wire protocol）在每个主题中作为实际取舍的对照片段出现。

## 问题定义

设计一个新协议之前，先回答「它要解决什么、明确不负责什么」。六个必须写下的问题：

1. **传输假设**：跑在什么之上？TCP 提供有序、可靠、字节流，则帧界、重传、按序由应用层负责，也不需自定义确认机制；UDP 之上则要自己做报文界（一次 recv 一个报文）、丢失/乱序/重复、以及是否确认。IP 组播/广播之上还要考虑多接收者的会话模型。
2. **消息模型**：请求/响应（一对一）、流水线（多个在途请求，需请求 ID）、发布/订阅（单向流）、还是流式（有头有尾的流，如 Kafka 消息流）？消息模型决定需要哪些字段。
3. **对象与语义**：传输的最小单元是什么（命令、事务、日志记录、帧）？有没有嵌套结构（数组、map、嵌套对象）？对象是自包含的，还是依赖连接状态（如 MySQL 的 `COM_STMT_PREPARE` 之后的语句 ID）？
4. **大小与频率**：单条消息多大（几十字节还是几十 MB）、多频繁、是否分批？这决定长度字段位数、是否要压缩、是否要复用连接。
5. **寿命与演进**：协议要不要跨版本兼容？需要兼容旧客户端/旧服务多久？这在第「版本兼容与灰度升级」节展开。
6. **明确不负责什么**：TLS 是否已负责加密与完整性？TCP 是否已负责可靠性？若已由下层负责，就不要再在自定义层重复实现（重复的校验与重传是常见的过度设计）。

三个对照片段的答案差异很大：

| | Redis RESP | MySQL 协议 | Kafka wire protocol |
| --- | --- | --- | --- |
| 传输假设 | TCP，一次一条命令，连接级流水线 | TCP，一个连接多阶段（握手→命令→结果） | TCP，长连接多路复用，多请求在途 |
| 消息模型 | 请求 = 命令数组；回复 = 类型标签标头 | 请求/响应，payload 按命令类型解释 | 请求/响应 + 每个 API 一种 payload |
| 最小单元 | 长度前缀的 bulk string / 数组 | 长度前缀的 packet，内部 payload | 长度前缀的 request/response 帧 |
| 状态依赖 | 无（命令自包含），例外：RESP3 push/订阅 | 强（能力位、预处理语句 ID、认证态） | 弱（连接级 API 版本，每个请求自包含） |

## 抽象对象

协议文档中出现的对象分为三类，设计时先列出这三张表，再编码：

- **会话对象**：连接状态、认证状态、协商出的版本、能力位集合、在途请求表。会话对象不出现在每个报文中，但决定报文如何解释。
- **消息对象**：请求、响应、通知/事件、心跳、ACK。消息对象是编码的基本单位。
- **字段对象**：长度、类型标签、请求 ID、版本、校验和、扩展位。字段对象决定消息如何被解析。

抽象对象是「在报文中可见」与「仅连接内可见」的分界线。MySQL 的 payload 按命令类型解释，意味着 payload 不是自描述的，解析必须依赖会话对象；Kafka 的 payload 也按 API 类型 + API 版本解释，同样依赖会话。RESP 的每条回复都以类型标签开头，是自描述的。设计时决定：**解析一条消息需要哪些上下文**——只靠消息本身（自描述），还是需要会话状态（节省字节、但耦合连接）？

## wire format 设计范式

wire format 回答「字节序列如何被切成有边界的消息，每条消息如何被解释」。按解析器的视角，一个报文依次要解决：**我在哪儿（帧界）→ 这是什么（类型）→ 有多长（长度）→ 对不对（校验）→ 怎么变（版本/扩展）**。

### 魔数（magic / signature）

固定字节前缀，用于识别「这是本协议的字节流」。

- 用途：端口复用时的内容识别、文件头识别、防止把不相干数据当报文解析、调试时快速辨认。
- 设计点：**魔数出现在帧界之后还是帧界之内**？TCP 之上必须先有帧界才有「开头」；UDP 之上一个报文天然是界。魔数长度要够长以避免误匹配（几个字节即可，越短误匹配概率越高）；缩短方式通常是「魔数本身兼作版本」，如 TLS record 用 `\x16` + 版本号。
- 成熟协议：TLS 的 `ContentType`（一个字节）+ version 二字节；PNG 固定八字节签名；MongoDB wire protocol 用四字节小端 `\x29\x00\x00\x00` 表示 "message"（每报文开头）。
- 陷阱：魔数在中间字段变化（如加密后），接收方先解密才能识别，识别点要随层变化移动。

### 长度前缀（length prefix）

在可变长度数据前显式给出长度，是 TCP 之上最通用的帧界手段，配合「读出长度 → 再读 length 字节 → 得到完整消息」的固定循环。

- 设计点：长度字段**定长**（如 uint32）还是**变长**（varint、compact）？定长解析快、实现简单，浪费几个字节；变长省字节，代价是解析循环里多一次分支。长度的**上界**是多少？uint16 只有 64KiB，uint32 是 4GiB——消息上限是协议的重要边界，必须显式写进规范。负数或长度大于剩余缓冲/超过上限，是解析器第一类必须拒绝的非法输入。
- **长度前缀与数据本身必须绑定在同一个状态里**：解析器「先读头、再读 body」是两阶段状态，见 state-machine.md 的帧状态机。若长度未校验就分配内存，长度字段会成为 DoS 向量（恶意对端声称 4GiB）；设计时应规定「读取长度后与本地上限比较，超限即协议错误」。
- 成熟协议：
  - RESP 的 bulk string `$<len>\r\n<data>\r\n`：长度在前、数据在后、尾部 `\r\n` 收尾，把「找 `\r` → 读长度 → 前进」当作一次原子操作，见 `src/upstream/redis/src/resp_parser.c:61` `parseBulk()`。长度字段用十进制 ASCII，人类可读但要多一步 `string2ll` 转换。
  - MySQL 的 packet header 是三字节小端长度（上限 16MB），payload 之外包四字节序列号。
  - Kafka 用四字节长度 + 二字节 API key + 二字节版本。单帧内多个数组/字符串元素再用各自的长度字段（`len`，compact 编码用 `ULEB128`）。

### 类型标签（type tag）

给每条消息一个显式的「这是什么」标签，让解析器按标签分发。

- 两种做法：**标签 + 长度前缀**（如 RESP 的 `*<n>\r\n` 数组、`$<n>` bulk），或**标签决定后面字段的布局**（TLV 与定长结构）。
- RESP 把类型标签放在每个值开头：`+` 简单串、`-` 错误、`:` 整数、`$` bulk、`*` 数组、`~` set、`%` map、`#` bool、`,` double、`_` null、`(` big number、`=` verbatim、`|` attributes。解析器 `parseReply()` 就一个按首字符的 switch（`resp_parser.c:210`），新增类型 = 新增一个分支 + 一个回调（`resp_parser.h:37` `ReplyParserCallbacks`）。这是「类型标签 + 回调分发」的教科书实现。
- MySQL 的 payload 无通用类型标签，靠命令编号（command number）区分 payload 布局；RESP3 自描述与 MySQL 上下文解释是两种极端，中间态是「版本 + 结构号」。

### TLV（Type-Length-Value）

`Type | Length | Value` 三元组，是协议设计中「可扩展结构」的基本单位。类型标签用掉若干字节，换来「未知类型可跳过、向后兼容、按需带字段」。

- 设计点：TLV 的 T 和 L 是**定长**还是**变长**；Value 是字节串还是可嵌套的 TLV 序列；TLV 的遍历终止条件是「流长度耗尽」还是「count 字段」。
- 递归 TLV（Value 内仍是 TLV）是「如何表达嵌套对象」的通用答案，代价是解析器递归，需要深度上限防栈溢出。
- 成熟协议对照：
  - TLS 的 record layer 即 TLV（type=ContentType，length=2 字节，value 用 `\r\n` 分隔的 handshake 消息），扩展结构用 `Extension | length | data` 支持扩展。
  - **DNS 的查询/回答部分、Kafka 的 metadata** 不是自描述 TLV，而是「版本 + 结构号」的定长结构，新增字段靠 bump 结构版本。Kafka 的 compact 编码（`compact array/string`）是对 TLV 的压缩变体：长度用 ULEB128，空值编码为 0。
  - 自描述 vs 紧凑的对立在这三例中非常明显：RESP 处处是 ASCII 标签，Kafka 只有头部类型标签 + 版本，内部布局按 schema。

### CRC / 校验和

校验和用于「在传输中间发现损坏」。设计点不是「要不要」，而是「谁已经做了」：

- **下层已做**（TCP checksum、TLS record MAC、以太网 CRC）：自定义协议层再加 CRC，增加开销而收益低。若传输假设为 UDP + 无加密，链路 CRC 只覆盖单跳，应用层数据可能被中转设备损坏而不被发现，此时应用层校验才有价值。
- **校验的是内容还是头部**：Kafka 的 CRC32C 覆盖整个请求/响应 payload；MySQL 的校验覆盖 payload；RESP 依赖 TCP 的校验，没有应用层校验。
- **完整性（integrity）≠ 防篡改（authenticity）**：CRC/校验和只能发现随机损坏，不能抵抗主动篡改；需要防篡改时用 MAC（HMAC、TLS 已内建），不要用 CRC 冒充安全机制。Kafka 在未启用 TLS 时用 CRC 发现损坏但不抗主动攻击。
- 设计上必须规定：**校验失败时是丢弃重传、关闭连接，还是直接拒绝该消息**？RESP 没有校验，损坏由 TCP 层兜底；Kafka 对 CRC 失败的响应直接报协议错误。

### 版本字段与扩展位

兼容性问题的解法分三层：**整体版本、per-结构版本、per-字段扩展位**。

- **整体版本 / magic 内嵌版本**：TLS record 的版本字段（见「魔数」节）；设计时决定「版本跟随连接还是跟随消息」。
- **per-API / per-结构版本**：Kafka 每个 API 独立版本（`api_version`），客户端和服务端各自维护「支持的最小/最大版本」，握手时协商出交集。MySQL 的 capability flags（能力位）则是**位集**形式，客户端发送 `CLIENT_CAPABILITIES`（`CLIENT_PROTOCOL_41` 等），服务端回 `SERVER_CAPABILITIES`，双方取交集后决定后续行为——本质上把「版本号」替换成「特性布尔集」。
- **扩展位（extension bits / reserved fields）**：在头部预留字段位，新功能先占用保留位，旧实现不认识时**必须按规范跳过**（skip-unknown），而不是报错。这是「向后兼容」与「向后不兼容」的开关：凡是「新增即改变解释」的位，都属于不兼容变更。
- 设计规则：**协商出的版本/能力是会话对象**，从握手那一刻起确定，之后的每个报文按协商结果解释（见「抽象对象」）。RESP 用 `HELLO` 命令协商版本（RESP2 ↔ RESP3）后，连接上每条回复的解释方式都改变——这是「连接级版本协商」；Kafka 是「API 级版本协商」，更细粒度。

## 核心机制

### 版本兼容与灰度升级

协议演进是设计方法论里最常被低估的部分。核心问题是：**新旧两端不可能同时升级，怎么让混存集群不宕**。

- **兼容策略四象限**（对新客户端 vs 旧客户端、新服务端 vs 旧服务端）：
  - *新客户端 × 旧服务端*：旧服务端不认识的字段必须可忽略。设计时给「未知扩展位/未知字段」规定默认语义（跳过、取默认值），否则新客户端一上线就炸。
  - *旧客户端 × 新服务端*：服务端必须能发现「对端不理解新特性」。靠协商（能力位交集）或检测（客户端版本字段），之后回退到旧语义。RESP 靠 `HELLO` 显式协商；MySQL 靠能力位交集；Kafka 靠 api_version 交集。
  - 两对之外，还有「同协议不同实现」的互操作性：规范要比实现严格。
- **灰度升级的具体机制**：
  1. 先让新服务端同时接受新旧两种消息（消息格式保持向后兼容，用扩展位新增）；
  2. 服务端全量替换后，才在客户端侧切换新格式（让每个请求/响应都显式带版本，避免依赖「隐式默认」）；
  3. 永远保留「协商失败则回退」的路径，回退不能依赖部署顺序。
  4. 新字段必须「可解析但可忽略」：解析器遇到未知字段号/类型标签时，长度已知就跳过，而不是丢弃整个消息。这是 TLV 结构（而不是定长结构）在演进上的最大优势。
- **成熟协议的对照**：Kafka 的 api_version 协议（请求里带版本，服务端返回 `Unsupported Version`，客户端据此回退）；MySQL 的 capability flags 逐位演进；RESP 从 RESP2 到 RESP3 用 `HELLO` 显式升级且不破坏旧客户端（旧客户端不发送 `HELLO` 就一直是 RESP2）。

### 错误模型

- **错误码的层次**：协议级（帧界错误、长度超限、CRC 失败）与业务级（命令不存在、权限不足、存储满）。协议级错误应在解析层统一处理（关闭连接或回错误帧），业务级错误走响应路径。RESP 把错误作为一等类型：`-ERR ...\r\n`，客户端通过 error 回调获得（`resp_parser.c:88` `parseError()`）；Kafka 每个响应第一个字段是 `error_code`。
- **错误是致命的还是可恢复的**：解析层协议错误（魔数错、长度非法）通常不可恢复→关闭连接；业务错误可恢复→返回错误码继续。不变量是「连接要么处于可用状态，要么被显式关闭，不允许半可用」。
- **错误的可观测性**：`-ERR` 之前不能有半条消息残留在连接里；发送方必须知道「我在错误的哪个边界」；参考 RESP 错误前导 `-` 让错误与正常回复区分开，且每条回复都是完整自包含的。

### 重传 / 幂等

- **下层已负责就不重复**：TCP 之上不需要消息层重传，但「对端崩溃后重试」需要消息层幂等（TCP 不保证「只执行一次」，只保证字节有序到达）。设计时明确：你的协议语义是 at-most-once / at-least-once / exactly-once？恰好一次需要请求 ID + 服务端去重，开销最高。
- **请求 ID 的两重作用**：乱序/多路复用时的匹配（一个连接多个在途请求），以及**幂等键**（同一 ID 重发，服务端识别并返回缓存结果）。
- 成熟协议：Kafka 的 producer 用 `producer_id` + 序号做幂等去重（at-least-once 上的去重）；MySQL 用四字节 sequence id 匹配响应并发现丢包；RESP 单连接顺序流水线，无请求 ID——它的「乱序匹配」需求为零，靠 TCP 保序。
- 超时：请求发出后必须有超时，超时后是重发还是报错取决于语义；超时是连接状态机的重要事件（见 state-machine.md）。

## 设计取舍

三个真实协议的取舍总结为一张表：

| 维度 | Redis RESP | MySQL 协议 | Kafka wire protocol |
| --- | --- | --- | --- |
| 二进制 vs 文本 | 文本（ASCII 标签 + 十进制长度） | 二进制（小端多字节整数） | 二进制（大端 + compact 变长） |
| 定长 vs TLV | 类型标签 + 长度前缀（等价的 TLV 思路） | 头部定长 + payload 按命令解释 | 头部定长 + 按 API schema 解释 |
| 自描述 vs 紧凑 | 强自描述（每条值带类型） | 弱（payload 依赖会话上下文） | 弱（依赖 api key + version） |
| 错误表达 | `-ERR` 一等类型 | 固定 error code + sqlstate | 响应首字段 error_code |
| 版本协商 | 连接级（HELLO） | 能力位位集 | 每 API 版本号 + compact |

取舍决策树：

1. **文本 vs 二进制**：需要人类可读、调试简单、与工具交互（`nc`、redis-cli）→ 文本；带宽/性能敏感、字段多、数字密集 → 二进制。文本省不掉长度前缀与转义（RESP 用 `\r\n` 收尾处理二进制数据）。
2. **定长 vs TLV**：字段集合稳定、字段少 → 定长（快、简单）；字段频繁演进、可选字段多 → TLV（可跳过未知类型）。定长结构演进必须依赖「版本号整体切换」，TLV 演进可以「原地加类型」。
3. **自描述 vs 紧凑**：每条消息独立可解析 → 自描述；消息内嵌 schema 信息 → 紧凑。自描述让「单条消息可独立测试、可重放」，紧凑让「头小、解析快」。Kafka 选了紧凑，代价是解析必须查 API schema；RESP 选了自描述，代价是每个值两个字符的类型开销。
4. **大端 vs 小端**：网络协议历史约定大端（Kafka）；REdis 依赖 ASCII 无字节序问题；MySQL 用 x86 风格小端。自定义协议选一种并写进规范，不要在实现里做「自动检测」。
5. **校验：跟随下层**：决定权在于「传输路径上有没有不可信的中间节点」。没有 → 不加；有 → 加 CRC，但 CRC 不替代 MAC。

## 不变量

设计协议时写下并一直维护的不变量，示例（本模块方法论要求每类设计至少列一条）：

1. **帧界不变量**：任何时刻，接收缓冲里的解析位置要么在消息边界，要么在一条约定的「头已读、body 待读」状态，不允许「部分字段被消费却无法回滚」。
2. **长度上界不变量**：任何长度字段在分配内存前必须已通过与本地上限的比较；解析器对「声称长度 > 剩余缓冲」一律拒绝。
3. **状态一致性不变量**：会话对象（版本、能力、认证态）只在握手/协商的确定点上改变，且改变是原子的；协商完成前，不使用未协商的语义解释任何消息。
4. **错误路径不变量**：协议错误要么让连接显式关闭，要么返回一个完整自包含的错误响应；不允许发送一半的错误帧后继续用同一个连接。
5. **版本协商不变量**：连接双方使用的解释规则，恒等于握手时协商出的最大公共版本；任何一方不得在协商之外「静默降级」。

## 边界条件与异常处理

按解析器的实际运行列出必须覆盖的边界，逐条给出行为：

| 边界 | 行为 |
| --- | --- |
| 连接建立后收到第一个字节不是魔数/合法标签 | 判定协议错误，关闭连接（不留半开放） |
| 长度字段为负（RESP `$-1` 是合法 null，其他负值非法） | 按规范区分「null 编码」与「非法长度」；非法即拒绝 |
| 长度字段声称的值 > 剩余缓冲 / > 本地上限 | 拒绝，不分配内存；可关闭连接或请求重传 |
| 消息被 TCP 分段/粘包（一次 recv 含多帧或半帧） | 解析器必须维持游标状态，支持增量解析（RESP 的 `curr_location` 即此用途） |
| 未知类型标签 | RESP：走 error 回调；设计规范时应决定「跳过」还是「报错」 |
| 未知扩展位/未知字段 | 跳过并继续（向后兼容），禁止整体丢弃消息 |
| CRC/校验失败 | 丢弃该消息；连续失败计数超限则关闭连接（防攻击） |
| 对端在消息中途关闭连接 | 丢弃半帧，按会话语义上报（请求可重发或报错） |
| 协商出的版本交集为空 | 拒绝连接并返回明确错误，不静默回退到旧版 |
| 长消息 / 大分配 | 长度上限先于分配；流式处理而非一次性拷贝到上限 |
| 并发/复用连接上的响应错配 | 请求 ID 或保序策略保证；响应到达先于其请求的请求 ID 视为协议错误 |
| 超时（无响应） | 按幂等策略重发或报错；超时作为状态机事件显式处理 |

这些边界统一对应到 state-machine.md 里的状态与转移，避免「解析行为」与「状态机行为」在文档中分叉。
