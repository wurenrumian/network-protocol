# 协议抽象与报文编码

## 定位

本模块是整个协议学习主干（`protocol-learning-design.md` §4.1）的第一个模块，任务是建立一套**分析语言**：一组跨协议通用的概念，用来观察和描述任意网络协议。它不追求全面实现，也不绑定单一主实现。

本模块确立的观察视角包括八个概念面：

- **报文布局**：header/payload、固定字段与可变字段如何组织；
- **字节序**：网络字节序（大端）的约定与转换；
- **长度与边界**：分帧、长度字段、定界符、截断与越界；
- **TLV**：Type-Length-Value 编码如何支持可变字段与扩展；
- **校验**：checksum / CRC / 认证标签各自的覆盖范围与强度；
- **版本/扩展**：字段升级、向后兼容与协商；
- **状态机**：协议行为如何被规范化（详见 `state-machine.md`）；
- **超时与错误模型**：无输入时状态如何推进、故障如何分类与传播。

在主干中，后续每个具体协议模块（Ethernet、IP、TCP、TLS、HTTP、QUIC……）都会反复用到这套概念。阅读任一具体模块时，如果遇到陌生的编码或边界问题，应回到本模块检索对应概念，而不是在具体模块内重新推导。

## 前置模块

无。本模块是主干起点，只需基本的 TCP/IP 分层直觉（五层模型、字节与二进制概念）。

它同时承担"为后续所有模块提供共同词汇"的角色，因此后续模块都隐式依赖本模块。

## 推荐阅读顺序

1. `protocol.md`：先读完问题定义与抽象对象，建立"协议在解决什么"的整体图景；
2. 按 `protocol.md` 的 wire format 小节顺序依次理解八个概念面：报文布局 → 字节序 → 长度与边界 → TLV → 校验 → 版本/扩展；
3. `state-machine.md`：把状态机当作分析工具掌握，重点是"如何从规范提取状态机"和"定时器驱动的异常路径"；
4. `references.md`：固定参考来源，按需查阅；
5. 进入下一个模块（Ethernet / VLAN / bridge，§4.2）时，把本模块概念与具体协议对照回看；每学完一个具体模块，回到 `protocol.md` 相应小节检查概念是否需要修正或细化。

建议每次进入一个新的具体协议模块前，先用本模块的八个概念面为该协议"列一张待确认清单"，再带着清单去读规范与源码，形成闭环。

## 源码入口

指向 `src/README.md`。

本模块**无单一主实现、无复制源码**（`src/upstream/` 为空）。`src/README.md` 维护一份"参考来源清单"：从 lwIP、BoringSSL、protobuf、quiche、nghttp2、nginx、Wireshark 等外部仓库中，按"文件 → 类别 → 阅读范围"列出用于归纳分析语言的具体文件与入口函数。这些文件均未复制进仓库，阅读时沿清单到对应上游仓库查看。

## 主实现 / 对照实现

本模块是方法论文档，`protocol-learning-design.md` §4.0 的主实现选型表不适用。归纳分析语言的参考来源为多个成熟实现的**公共抽象**：

- **lwIP**：校验和、字节序宏、IPv4/TCP 头部解析、TCP 定时器；
- **BoringSSL**：record 层的长度与加密边界；
- **protobuf**：varint / tag 的紧凑整数与 length-delimited 编码；
- **quiche**：QUIC VarInt、packet 编码与版本协商；
- **nginx / nghttp2**：流式分帧与帧类型；
- **Wireshark** dissector：作为"从字节流反推字段结构"的观察参照。

选择这些来源的标准是：覆盖本模块八个概念面中最典型的实现形态，且相互之间能形成对照（例如 lwIP 的 16 位校验和与 TLS 的 AEAD 认证标签对照"错误检测 vs 完整性保证"）。
