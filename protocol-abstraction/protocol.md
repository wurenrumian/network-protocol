# 协议抽象与报文编码 · protocol

本文件建立"协议抽象与报文编码"的分析语言。它回答的问题是：**当两个（或多个）不共享内存、不共享时钟的进程要通过不可靠、有损、有延迟的通道通信时，它们如何就"一段字节流的含义"达成一致，并在出错时如何感知与恢复。**

协议本身是约束（约定字节的排布与含义），实现是这些约束的落地。本文件只讲约束及其设计规律；实现形态在后续具体模块中展开。

## 1. 问题定义

### 1.1 协议要解决什么

把"通信意图"压缩为一串对端能无歧义解读的比特，并支撑对端据此做出正确的推进（状态转移）。具体子问题：

- **编码（encoding）**：如何把结构化数据映射为比特，使对端能无歧义还原；
- **分帧（framing）**：对端如何从连续字节流中知道"一个报文到哪里结束"；
- **寻址与标识**：如何区分多个对端 / 多个会话（本模块只涉及"一个报文内如何标识"，跨层寻址在链路层 / 网络层模块展开）；
- **可靠性（子集）**：如何检测损坏、丢失、乱序并恢复（完整机制在传输层模块展开，本模块只建立"校验与错误模型"这个分析框架）；
- **演进**：协议发布后如何修改而不破坏已有实现。

### 1.2 协议明确不负责什么

- 不负责通道本身（物理层 / 链路层丢包、重排、损坏由下层或上层机制处理，协议只负责描述自己视角内的错误模型）；
- 不负责"数据语义"，只负责"数据形态"：一个 TLV 字段的字节含义由应用决定，协议只保证它如何被分帧、校验和还原；
- 不保证实时性、吞吐上限（这是调度与实现问题，不是编码问题）；
- 不保证安全（认证、机密性由专门层如 TLS 处理；普通校验和只能检测损坏，不能防恶意篡改）。

## 2. 抽象对象

协议在概念上操作的抽象对象，独立于具体实现：

| 抽象对象 | 定义 | 典型实现（后续模块） |
| --- | --- | --- |
| **报文 / 帧 / 数据报（packet / frame / datagram）** | 一次独立传输的字节单元，有完整边界 | 以太帧、IPv4 报文、UDP 数据报 |
| **流（stream）** | 由多个报文按序构成的字节序列，报文边界可被丢弃 | TCP 字节流、TLS record 之上还原的应用数据 |
| **头（header）与载荷（payload）** | 报文内部两个角色：头携带元数据，载荷携带用户数据 | IP 头 / TCP 头之后的部分 |
| **字段（field）** | 头中一个有固定含义、固定长度或可变长度的单元 | type、length、checksum |
| **会话（session）** | 一次端到端交互的状态集合，跨多个报文 | TCP 连接、TLS session |
| **端点（endpoint）** | 参与通信的一方，有唯一标识 | IP:port、TLS 中的连接双方 |
| **TLV 元素（Type-Length-Value）** | 一种可变字段的通用编码单元 | DHCP options、TLS extensions、QUIC transport parameters |

## 3. wire format

wire format 是协议的"字节视图"：给定一段字节流，能无歧义地还原出它的字段结构。设计 wire format 时反复出现的核心决策是 **长度与边界**、**字节序**、**TLV 与可变字段**、**校验与完整性**、**版本与扩展**。下面按本模块分析语言逐一展开。

### 3.1 报文布局

报文的宏观组织方式，决定了解析器的复杂度。

- **固定头部 + 固定尾部**：所有字段长度固定、位置固定，解析 O(1)、可随机访问；代价是灵活性差（IPv4 的最小 20 字节头）。代表：TCP 头、IPv6 固定头、ICMP。
- **头部 + 可变载荷**：载荷长度由头部长度字段或外部边界（如链路层长度）决定。代表：IPv4（IHL + Total Length）、以太帧。
- **头部 + 多段（分块）**：可变部分拆为若干同构块，每块自带长度或由块类型驱动。代表：TLS handshake 消息序列、HTTP chunked 编码、MPEG-TS。
- **分层嵌套**：一个报文的载荷是另一个协议的报文（封装）。协议分层正是这种布局的复用：IP-in-Ethernet、TCP-in-IP、TLS record 内再分层。嵌套边界就是各层长度字段的衔接点。

**布局的解析顺序**：解析器总是"先固定部分，后可变部分"：先读固定头，得到长度、类型、偏移，再依此定位可变区域。任何"先读可变部分"的设计都会导致解析器必须猜测边界，是反模式。

### 3.2 字节序

字节序是多字节字段在 wire 上的排列方式，是第一个"无歧义"障碍。

- **大端（网络字节序，big-endian）**：最高位字节先发，是事实上的网络标准（Internet Protocol 的 `htons/htonl/ntohs/ntohl` 约定）。含义是：多字节整数的字节顺序按数值从左到右。
- **小端（little-endian）**：最低位字节先发，常见于 x86 主机内部；wire 上用小端是特例，必须显式说明（如某些嵌入式 / 专有协议）。
- **字节序转换**：`htons/htonl`（主机序 → 网络序）、`ntohs/ntohl`（网络序 → 主机序）在几乎所有协议栈实现中以宏或函数存在（lwIP 的 `src/include/ipv4/ip4.h`、BoringSSL 的 `crypto/cipher/...` 内部均通过显式函数处理）。理解重点是：**协议只定义 wire 字节序，不定义主机序**；实现负责在边界转换，且转换必须覆盖所有多字节字段，漏掉一个就是 bug。
- **比特序 vs 字节序**：某些协议字段以"比特"为单位定义（如 IP 头中的 version 占 4 比特、IHL 占 4 比特），此时还涉及比特序（MSB-first / LSB-first）。主流协议（IPv4/IPv6/TCP/TLS）均按**字节内 MSB 在低地址**解释，即大端比特序。若协议不明确，必须固定说明，否则解析器双方可能歧义。

**不变量**：一个多字节字段在 wire 上的字节顺序，必须与解析器读取该字段的方式一致；发送端转换后的字节与接收端还原后的数值必须相等。

### 3.3 长度与边界

长度与边界是分帧的核心，也是 wire format 中出错率最高的部分。它回答：**解析器如何知道"读到这里为止就是下一个字段 / 下一个报文"？**

边界判定的三种手段（可组合使用）：

1. **外部定界**：由下层提供边界（如以太帧长度由链路层给出、TCP 边界由流中长度字段 + 流终止界定、IP 报文边界由链路层或分片重组界定）。代表：IPv4 的 Total Length 字段、以太帧由帧间距（IFG）界定、UDP 长度字段。
2. **内部定界（length-delimited）**：报文 / 字段内自带长度字段。这是最常用也最稳的手段：解析器先读长度，再按长度切片。代表：TLV 中的 Length、TLS record 的 16 位 Length、HTTP Content-Length。
3. **定界符（delimiter）**：用特殊字节序列标记结束（HTTP/1.1 的 `\r\n`、SMTP 的点行）。简单但存在**转义 / 歧义**问题：内容中出现定界符怎么办？必须用转义（如 SMTP 的 `..` 转义）或内容长度做双重确认。现代设计优先用 length-delimited 而非 delimiter，避免转义复杂度。

**长度字段本身的设计**：
- **固定宽度 vs 可变宽度**：固定宽度（如 UDP 的 16 位、TCP 的 16 位窗口）简单但有限；可变宽度（QUIC 的 VarInt、protobuf 的 varint）节省字节但增加解析复杂度（需判断字节数）。protobuf 用 varint 的变长整数，QUIC 用前两位作长度指示的 VarInt（`src/core/packet/...` 中的 `read_varint` 等）。
- **最大长度约束**：每个长度字段都应有一个可编码上限（如 16 位最大 65535）；超过上限时要么分片（TCP 分段、IPv4 分片），要么报错。**解析器必须验证收到的长度 ≤ 缓冲区/报文剩余空间**，否则是缓冲区溢出 / 长度前缀注入（integer overflow）的经典漏洞来源。
- **最小长度**：空报文是否合法、长度 0 的载荷是否有意义，需明确。

**边界与截断**：解析器必须处理"报文被截断"（收到长度 > 实际可读字节）与"报文过长"（收到长度 > 分配缓冲区）两种情况，分别对应"丢包/分片导致的不完整报文"和"恶意或损坏的长度字段"。解析器应在**固定长度之后立即验证剩余长度 ≥ 必需字段长度**，而非在最后一次性检查。

**不变量**：
- 所有长度字段编码的上界 ≥ 报文实际内容的字节数；解析器收到的 length 必须小于等于可用数据长度；
- 若协议允许分片/重组，分片后的总长度必须等于原始报文长度（见 IPv4 分片、TCP 分段）；
- 若长度字段与载荷内容冲突（内容自身含有结束标记），以长度为准（length-delimited 优先于 delimiter）。

### 3.4 TLV

TLV（Type-Length-Value）是可变字段的通用编码单元，是"固定头部 + 可变扩展"的标准手段。

```
+--------+--------+------------------+
| Type   | Length | Value            |
+--------+--------+------------------+
```

- **Type**：字段类型标识，决定 Value 的解释方式（通常用整数或短字符串，见 DHCP option type、TLS extension type、protobuf field tag）；
- **Length**：Value 的字节数（长度字段，见 3.3）；
- **Value**：字段内容，类型与长度决定其结构。

**TLV 变体**：
- **TTLV**（Type + Type 变体，如 TLS extension 的 `type + length + data` 中 type 又分多种）；
- **TLV 嵌套**：Value 内部又是一个 TLV 序列（如 protobuf 中 message 字段的递归）；
- **无 Length 的固定 TLV**：Value 长度由 Type 决定（如部分二进制协议），此时不能称为严格 TLV，属于"type-driven fixed-size"；
- **TLV 与边界**：多个 TLV 顺序排列时，靠每个 Length 连续定位下一个 TLV（`pos += len(header) + length`）。

**TLV 的取舍**：
- 优点：新增字段不改动已有字段布局，向后兼容扩展（见 3.6）；解析器可按类型跳过未知字段；
- 缺点：多 1 字节类型 + 长度开销；长度字段的存在使解析必须顺序扫描（无法随机访问）；若类型重复、类型未知、长度超限处理不当，会引入歧义。
- **未知类型处理**：协议必须定义"收到未知 Type"的行为：忽略 / 报错 / 跳过并继续。TLS 对未知 extension 一般"忽略且不协商"；DHCP 对未知 option 忽略。**这决定协议的可扩展性**。

**不变量**：
- 单个 TLV 的 Length 必须覆盖其 Value 的完整字节数，且 Type 必须能唯一定义 Value 的解释；
- 顺序解析 TLV 序列时，`pos + Length` 必须 ≤ 报文边界；
- 若协议禁止重复 Type，则同一 TLV 序列中 Type 不应重复（协议需声明约束）。

### 3.5 校验（checksum / CRC / 认证）

校验回答：**对端如何发现报文在传输中被破坏？** 三层强度：

- **弱校验（普通 checksum）**：对字段做加法/异或，覆盖有限，检错能力弱。代表：IP 头校验和（16 位补码和，只覆盖 IP 头，`lwIP src/core/ipv4/ip4.c` 的 `ip4_checksum`）、TCP/UDP 校验和（覆盖伪首部 + TCP/UDP 头 + 载荷，`lwIP src/core/tcp_in.c`）。
- **强校验（CRC）**：多项式除法式校验，检错能力强（CRC32 可检测所有长度 ≤ 32 位的单比特错误、所有奇数个错误、突发错误）。代表：以太帧的 FCS（CRC32）、Wi-Fi 帧 CRC。
- **完整性保证（MAC / AEAD 认证标签）**：用密钥保护，同时检测篡改与损坏，不可伪造。代表：TLS record 的 AEAD（AES-GCM 的 GCM tag）、IPv6 的 IPsec AH。这是"错误模型"从"检测损坏"升级为"检测篡改"的界限。

**校验的覆盖范围**：校验覆盖哪些字节是设计决策：
- **伪首部（pseudo-header）**：TCP/UDP 校验和把"源 IP + 目的 IP + 协议号 + 长度"伪首部纳入，防止跨层"地址被改而校验不被发现"（因 IP 头校验只覆盖 IP 头，不覆盖载荷，所以传输层必须自己覆盖伪首部）。
- **只覆盖头 vs 覆盖整包**：IP 只校验头（载荷由上层负责）；以太只校验帧（不含 Preamble）；TLS record 校验整个 record 的密文。
- 校验在**分片后**是否重新计算：IPv4 分片后每个分片重新计算 IP 头校验和（载荷校验如 UDP 在分片前计算，重组后不变）。

**校验强度与位置的取舍**：校验强但成本高（CPU 时间）；不校验则损坏不被发现。协议常分层：链路层 CRC 负责物理层错误，传输层校验和负责端到端（覆盖范围跨越中间节点），应用层再叠加应用校验（如 HTTP 报文后的校验）。

**不变量**：
- 接收方对收到的报文校验失败，必须**丢弃该报文且不向协议上层推进**（不能把损坏报文当有效数据处理）；
- 校验覆盖范围必须包含"报文中所有对端会依赖的字段"（IP 校验覆盖头、TCP 校验覆盖伪首部 + 载荷）；
- 发送方在构造报文后、发送前必须完成校验计算，且校验字段不能在自己计算时覆盖自己（计算时校验字段置零）。

### 3.6 版本 / 扩展

版本字段回答：**协议发布后，如何在不破坏已有实现的前提下演进？**

- **版本字段（version）**：报文头的第一个字段常是版本号（IPv4 的 4 位 version、TLS record 的 2 字节 version、HTTP 的 HTTP/x.y、DNS 的 opcode 等）。解析器先读版本，再按对应版本解释后续字段。**同一版本字段下，后续字段的含义可以随版本变化**（如 IPv6 完全重新定义了 IPv4 的头）。
- **扩展机制**：
  - **option / extension 字段**：固定头之外附加的可变字段（IPv4 Options、TCP Options、TLS extensions、DHCP options、HTTP headers）。新功能通过新增 option 实现，旧实现忽略未知 option。
  - **版本协商（version negotiation）**：双方就共同支持的版本达成一致。TLS 1.3 用 `supported_versions` extension 协商；QUIC 用 Version Negotiation 报文（`quiche` 的 `src/lib/...` 中处理）。协商失败时协议需定义降级或拒绝路径。
  - **feature flag / capability**：不升版本，用标志位声明能力（如 TCP 的 MSS/Window scale option、HTTP/2 的 SETTINGS）。
- **向后兼容（backward compatibility）**：旧实现能否读新报文？分两类：
  - 新增字段**位置在固定头之后**（TLV / extension），旧实现按长度跳过 → 兼容；
  - 新字段**改变了固定头语义**（版本号不同、字段含义变更）→ 不兼容，必须用版本号区分。
  现代协议的趋势：**用版本号做不兼容变更，用 extension 做兼容变更**。禁止"不升版本却改变固定字段语义"，否则会静默产生歧义（同一字节两个含义）。
- **协议版本与实现版本分离**：wire 上的版本号是协议版本，不是实现版本；一个实现可以同时支持多个 wire 版本。

**不变量**：
- 同一版本号必须对应唯一确定的字段解释，不允许同一版本内出现两种解释；
- 新版本不得改变旧版本的合法报文语义，除非用新版本号显式区分；
- 解析器对未知版本应明确拒绝或协商，不能"假装理解"而误解析。

## 4. 核心机制

### 4.1 编码——把抽象对象映射到字节

编码机制是把字段映射到 bit 的规则。常见编码形态：

- **定长编码**：固定长度字段，位置固定，解析快，浪费带宽（IPv4/TCP 头中很多字段）；
- **变长整数（varint）**：用 7 位一组、最高位做续延标记（protobuf），或用长度指示前缀（QUIC VarInt 前两位指示后续字节数）。节省字节，但需处理截断（解析器必须检查"数字是否完整到达"）；
- **长度前缀 / length-delimited**：见 3.3；
- **定界符 + 转义**：见 3.3，现代设计尽量避免。

**编码的层次**：编码不是一次完成的。抽象对象 → 结构化表示（struct）→ wire 字节序列，这是**序列化（serialize）**；反向是**反序列化（deserialize / parse）**。序列化与解析的对称性是协议实现的第一不变量：**发送方编码的结果，接收方解码必须还原出等价的抽象对象**。所有协议实现都通过成对的 `encode()`/`decode()`、`pack()`/`unpack()`、`htons`/`ntohs` 对称函数来保证这一点。

### 4.2 解析（parse）——从字节到结构

解析器是对 wire format 的落地。解析顺序严格遵循布局：固定头 → 长度/类型 → 可变区。**解析器的每一步都必须显式处理"剩余字节不足"**（见 3.3）。解析器应该：

- 先读固定头，验证版本、长度是否合法；
- 依长度字段定位可变区，逐字段按类型解析；
- 对未知类型按协议规则处理（忽略 / 报错）；
- 解析完成后验证"已消耗字节 = 报文长度"（防长度字段与内容不一致的歧义）。

**解析失败模型**：解析失败（长度不足、非法类型、校验失败）时，协议需定义是"丢弃报文继续"还是"终止会话"。UDP 丢弃单个数据报；TCP 对损坏段丢弃但连接继续；TLS record 校验失败直接触发连接终止（因为完整性被破坏，继续会话不安全）。

### 4.3 状态机与定时器（与 state-machine.md 的接口）

报文编码之后，协议还需在**时间维度**上规定行为：什么条件下允许发送、收到什么事件推进到哪一状态、长时间无输入怎么办。这部分见 `state-machine.md`。本模块只建立约定：**状态机决定"如何对一组合法报文序列做出反应"，定时器把"无输入"转化为显式事件**（重传、超时、清理），使协议的完整行为是"状态 + 事件 + 定时器"三者的组合。

### 4.4 错误模型（error model）

错误模型是协议对故障的**分类与处置策略**，是本模块最重要的分析语言之一。按发生位置分：

- **编码错误（本协议内）**：字节序错误、长度错误、非法字段值。处置：解析失败，丢弃报文，按协议错误处理。
- **传输错误（下层/通道）**：位损坏、丢包、乱序、重复、延迟。处置：下层（链路 CRC、网络层校验）与上层（传输层校验、序列号、重传）分层处理。
- **对端错误（对端行为异常）**：对端违反协议状态机（非法状态转移）、恶意输入。处置：校验失败丢弃、关闭连接、报错。**恶意输入是安全视角的错误模型**（解析器必须在所有入口防长度/类型攻击）。
- **超时（无对端响应）**：对端无响应不等于对端崩溃，只能以超时作为上限。处置：重传、放弃、宣告不可达。

**错误处置的层级化**：一个错误应先在最近的边界处置（链路层丢弃损坏帧），只有需要端到端语义时上交给上层（TCP 的端到端校验）。**不能把下层错误不加处理地泄漏给上层**，否则上层无法区分"真实错误"与"下层噪声"。

**错误处置的对称性**：协议双方对同一错误类型应采取对称策略（对端超时重传，本地也必须超时重传），否则产生状态不一致（见 state-machine.md 的正常/异常时序）。

## 5. 设计取舍

| 取舍 | 选项 | 后果 | 实例 |
| --- | --- | --- | --- |
| 分帧 | length-delimited vs delimiter | 前者稳、可防歧义；后者简单但需转义 | HTTP/1.1 `\r\n`（delimiter）vs TLS record / TCP（length） |
| 长度字段 | 固定宽度 vs varint | 前者解析简单、有上限；后者省字节、解析复杂 | UDP 16 位 vs QUIC VarInt |
| 校验强度 | 头校验 / 整包校验 / 认证 | 头校验快、覆盖窄；认证最强但最贵 | IP 头校验 vs TCP 伪首部校验 vs TLS AEAD |
| 版本演进 | 版本号 vs extension | 版本号破坏兼容、防歧义；extension 兼容、需处理未知类型 | IPv4→IPv6 vs TLS/HTTP headers 扩展 |
| 可变字段 | TLV vs 固定布局 | TLV 灵活可扩展、顺序解析；固定布局快但僵化 | DHCP options vs IPv4 固定头 |
| 边界确认 | 解析时逐步验证 vs 结束后统一验证 | 前者更安全、更早失败；后者代码少但风险高 | TLS/BoringSSL 的 record 解析（逐步） |
| 错误处置 | 丢弃继续 vs 终止会话 | 前者健壮、静默；后者明确、可能不可用 | UDP 丢弃 vs TLS 记录校验失败终止 |

## 6. 不变量（汇总）

1. **编码对称性**：发送方编码 → wire 字节 → 接收方解码，必须还原等价抽象对象；
2. **版本一致性**：同一版本号对应唯一字段解释，未知版本必须显式拒绝或协商；
3. **长度一致性**：所有长度字段的上界 ≥ 实际内容长度；解析器收到的 length 必须 ≤ 可用数据；
4. **边界一致**：解析消耗的字节数必须等于报文/字段的声明长度；
5. **校验覆盖**：校验覆盖所有依赖字段；校验失败必须丢弃，不得向上层推进；
6. **错误处置对称**：协议双方对同类错误的处置策略对称，避免状态分裂；
7. **解析安全**：解析器在所有入口验证长度与类型，防恶意输入（安全视角的不变量）；
8. **扩展安全**：扩展字段（extension/TLV）不得改变旧版本固定字段语义，未知类型行为必须显式定义。

## 7. 边界条件与异常处理

- **零长度报文**：空载荷是否合法（UDP 允许、TCP 不携带数据的 ACK 合法、HTTP 空 body 需明确）；
- **最大长度报文**：长度字段上限、MTU 限制、分片重组（IPv4 分片、TCP 分段）与"长度超 MTU"处理；
- **截断报文**：收到长度 > 剩余字节 → 丢弃 / 等待重组（TCP 重组、TLS record 重组）；
- **重复 / 乱序**：由序列号（TCP）、数据报 ID + 分段（IP）处理，见传输层模块；
- **长度字段为 0**：语义需明确定义（TLS record 长度 0 是合法 ping？TCP 0 窗口通告是合法 ACK？）；
- **非法类型值**：未知 type / option / extension / 非法版本 → 按协议定义忽略或报错；
- **校验失败**：丢弃并记录，不得向上层推进；若校验覆盖头且头被改（如 IP 头校验失败），连"可信的"数据都不能假设；
- **发送方字节序 / 长度溢出**：发送时长度字段溢出（数据超过字段上限）必须提前截断或报错，不能静默截断；
- **解析器攻击面**：所有边界（长度、类型、嵌套深度、重复字段）都是攻击面；解析器必须假定输入不可信（见 TLS/BoringSSL 的 record 解析对长度和类型的严格检查）。
