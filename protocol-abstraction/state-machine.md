# 协议抽象与报文编码 · state-machine

状态机是协议行为在**时间维度**上的规范化：它规定"在什么状态下，收到什么事件，做什么动作、转移到哪个新状态"。本文件先建立"状态机作为分析工具"的通用框架（因为本模块是方法论文档，不绑定某个具体协议），再用一个带重传的简单协议演示如何把规范落到状态机上，并给出正常 / 异常时序。

## 0. 为什么协议需要状态机

协议双方不共享内存、不共享时钟，只能通过报文交换推进。由此产生三个必须回答的问题：

1. **合法性**：双方如何判断"这条报文在我当前状态下是合法的"？——需要显式状态；
2. **确定性**：同一状态下收到同一事件，双方必须产生同一行为，否则状态分裂；——需要确定性转移函数；
3. **无输入的推进**：对端不回应时怎么办？——需要定时器把"无事件"转化为"显式事件"。

状态机回答 1 和 2；定时器（见 §4）补充回答 3。两者共同构成协议的**时间语义**。

## 1. 状态机作为分析工具

阅读任意协议源码前，先按以下方法提取状态机，再带着状态机进入源码验证（问题驱动闭环）。

### 1.1 从规范中提取状态机的步骤

1. **找状态变量**：协议中"随报文推进而变化的记忆"就是状态。显式状态（TCP 的 LISTEN/ESTABLISHED/FIN-WAIT，TLS 的 ClientHello/ServerHello…）与隐式状态（TCP 发送/接收窗口、序号）都是状态。
2. **找事件集**：事件分两类——
   - **报文事件**：收到某个报文（到达某个阶段）；
   - **本地事件**：应用调用（connect/send）、定时器到期（重传计时、keepalive）、对端行为（异常报文）。
3. **画转移表**：状态 × 事件 → (动作, 新状态)。关键是把"未定义的 (状态, 事件) 组合"显式标出：它们是**错误路径**，协议必须定义处理（丢弃 / 重置 / 终止），不能留白。
4. **标注动作与副作用**：转移往往伴随动作（发送 ACK、重排、释放资源）。动作不在状态内，但影响状态变量。
5. **找定时器**：每个定时器是一个"未来事件发生器"，必须在状态机中占一个事件槽位（见 §4）。

### 1.2 状态机的常见形态

- **生命周期状态机**：连接从建立到关闭的状态序列（TCP 的 11 状态、TLS handshake 的状态、HTTP 请求-响应状态）。特征：状态数少、转移密集、每个状态对应"下一步能收到什么"。
- **协议会话状态机**：一个会话内部的子状态（TLS record 层的连接状态 = 密钥、序号、未完成输入缓冲）。
- **隐式状态机（滑动窗口 / 序号）**：不是显式 enum，而是由窗口边界、序号等连续值决定的合法性判断（TCP 序号合法性 `SEG.SEQ <= SND.NXT && SND.UNA <= SEG.SEQ`、QUIC packet number 空间）。**这类状态最难调试**，因为"合法与否"不是一个离散枚举。
- **分层状态机**：一个协议对象含多层状态（TCP 连接状态 + 定时器状态 + 拥塞控制状态）。分析时把层次分开，避免混为一谈。

### 1.3 状态机分析的价值

- **找错误路径**：完整转移表能暴露"未定义行为"，即安全漏洞与状态分裂的根源（例：TLS 1.2 对 TLS 1.3 报文的处理错误导致三态（3Shake）攻击）。
- **验证对称性**：双方状态机是否镜像对称（一方 FIN-WAIT，另一方必须对应 CLOSE-WAIT），对称性破坏 = 状态分裂。
- **反推定时器语义**：每个超时分支对应"没有对端回应"的假设，定时器值的选择反映对"网络延迟上界"的估计。

## 2. 状态、事件、状态转移（通用框架）

| 要素 | 含义 | 分析时必须回答的问题 |
| --- | --- | --- |
| **状态 S** | 协议对象所处的合法配置 | 状态有多少种？初始状态？终态？哪些状态可达？（死状态、不可达状态是设计错误） |
| **事件 E** | 报文到达 / 定时器到期 / 应用调用 | 事件集是否封闭？是否覆盖所有输入？ |
| **转移函数 δ(S, E) → (A, S')** | 事件下的动作与状态变化 | 每对 (S, E) 是否有定义？(S, E) 未定义时协议如何处理？ |
| **动作 A** | 发送报文、更新变量、释放资源 | 动作与状态是否一致？动作是否会产生新事件（如发 ACK 触发对端回 ACK）？ |
| **初始 / 终态** | 会话开始与结束 | 未建连接收到数据？连接已关收到数据？均需定义。 |

**转移的三种类型**：
- **自转移**（S→S）：动作改变变量但不改变状态（TCP 在 ESTABLISHED 收到数据段 → 更新窗口 + 回 ACK，状态不变）。
- **推进**（S→S'）：状态前进（SYN_SENT → ESTABLISHED）。
- **回退/重置**（S→S' 其中 S' 是错误或初始态）：协议失败、超时、对端异常（超时重传失败 → 连接重置）。

## 3. 示例：一个带重传的简单请求-响应协议

下面用一个虚构的"可靠请求-响应"协议（RECHO，Request + Echo）演示完整流程。它在一个不可靠通道上运行，只含一个请求（REQUEST）与一个应答（REPLY），REQ-ID 用于去重（允许重复报文），超时重传，超过重传上限则宣告失败。这个例子集中了本模块分析语言里"状态 + 定时器 + 错误模型"的交互。

### 3.1 报文（wire 简表）

```
REQUEST: type=1 | req-id (16b) | payload-len (16b) | payload
REPLY:   type=2 | req-id (16b) | status (8b) | echo-len (16b) | echo
NACK:    type=3 | req-id (16b)           (对端无法处理时快速失败)
```

### 3.2 状态集

| 状态 | 含义 |
| --- | --- |
| `IDLE` | 初始态：无在途请求 |
| `WAIT_REPLY` | 请求已发出，等待应答（可多次重传） |
| `DONE` | 收到有效 REPLY/NACK，交付结果 |
| `FAILED` | 重传超限 / 对端 NACK，宣告失败 |

### 3.3 事件集

| 事件 | 来源 |
| --- | --- |
| `app_request(payload)` | 应用调用 send |
| `recv(REPLY)` | 对端应答 |
| `recv(NACK)` | 对端明确拒绝 |
| `recv(OTHER)` | 类型 / 校验非法、req-id 不匹配等 |
| `timer_expiry(retx)` | 重传定时器到期 |
| `timer_expiry(retx_limit)` | 重传次数达到上限 |
| `app_cancel()` | 应用放弃等待 |

### 3.4 转移表

| 状态 | 事件 | 动作 | 新状态 |
| --- | --- | --- | --- |
| `IDLE` | `app_request` | 生成 req-id，置重传计数=0，发 REQUEST，启动重传定时器 | `WAIT_REPLY` |
| `WAIT_REPLY` | `recv(REPLY)` 且 req-id 匹配 | 停止定时器，交付结果 | `DONE` |
| `WAIT_REPLY` | `recv(NACK)` | 停止定时器，交付失败 | `FAILED` |
| `WAIT_REPLY` | `recv(OTHER)` | 丢弃（校验失败 / 类型非法 / req-id 不匹配） | `WAIT_REPLY`（自转移） |
| `WAIT_REPLY` | `timer_expiry(retx)` | 重传计数+1；若 < 上限：重发 REQUEST、重启定时器；否则：交付失败 | 重传：`WAIT_REPLY`；超限：`FAILED` |
| `WAIT_REPLY` | `app_cancel` | 停止定时器 | `IDLE` |
| `DONE` / `FAILED` | 任何事件 | 丢弃 | `DONE` / `FAILED`（终态，自转移） |
| `IDLE` | 收到任何报文 | 丢弃（无在途请求，非法） | `IDLE` |

**关键点**：
- **`recv(OTHER)` 的自转移**：校验失败、req-id 不匹配的应答必须"被忽略而不推进状态"。若错误地推进到 `DONE`，就违反了 protocol.md §6 的"校验失败不得向上层推进"不变量。
- **定时器是事件源**：`timer_expiry(retx)` 被建模为普通事件，使"无对端回应"不再是无行为，而是触发显式转移。超时重传的上限把状态机从"无限等待"约束为"有限失败"。
- **对称性**：本地超时重传，对端也会因为乱序/重复重复收到 REQUEST；对端用 req-id 去重（同 req-id 重复请求 → 重复应答），这是"重复事件"的错误模型处理。这正体现了"双方对同类错误的处置对称"不变量。

### 3.5 正常时序

```
发起方 (RECHO client)              对端 (RECHO server)
  IDLE ── app_request ─────────────►
  WAIT_REPLY ── REQUEST ───────────►  收到 REQUEST，处理，构造 REPLY
                                    ◄── REPLY ── WAIT_REPLY
  DONE ── 交付结果
```

### 3.6 异常时序（丢包 + 重传 + 去重）

```
发起方                              对端
  IDLE ─ app_request
  WAIT_REPLY ─ REQUEST (1) ────────► (网络丢失，对端未收到)
  WAIT_REPLY ─ timer 到期
  WAIT_REPLY ─ REQUEST (2) ────────► 收到，处理，发 REPLY
  WAIT_REPLY ◄── REPLY ────────────  (REPLY 重复，因 REQUEST 乱序可能重复)
  DONE
```

### 3.7 异常时序（对端无响应 → 失败）

```
发起方                              对端
  WAIT_REPLY ─ REQUEST (1)
  WAIT_REPLY ─ timer 到期
  WAIT_REPLY ─ REQUEST (2)
  WAIT_REPLY ─ timer 到期 ─── 重传计数达到上限
  FAILED ─ 交付失败（宣告对端不可达）
```

### 3.8 从示例推广

这个示例不涉及任何真实协议，但它演示了**所有**带可靠性协议的共同骨架：

- 状态：`初始 → 在途 → 完成/失败`；
- 事件：应用调用 + 对端报文 + 定时器到期；
- 错误模型：非法报文（丢弃）、重复报文（去重）、无响应（重传、超限失败）；
- 对称性：对端的去重逻辑与发起方的重传逻辑相互配合。

把这套骨架套用到 TCP（`CLOSED → SYN_SENT → ESTABLISHED → ...`，重传、RTO 超时）、TLS（`ClientHello → ServerHello → ...`）、HTTP（`请求 → 响应`）等真实协议时，只需替换具体事件与状态名——这正是"状态机作为分析工具"的价值。

## 4. 定时器与超时

定时器是"无输入时状态的推进器"：它把"对端沉默"转化为显式事件。

| 定时器类型 | 触发的事件 | 典型转移 | 代表的协议假设 |
| --- | --- | --- | --- |
| **重传定时器（retransmission）** | 超时 → 重传 | 原地自转移（重传不改变状态） | "对端可能没收到，网络可能丢包" |
| **重传上限 / 宣告失败** | 重传次数达上限 → 失败 | `WAIT_REPLY → FAILED` | "对端不可达，继续重传无意义" |
| **会话超时（idle timeout）** | 长时间无报文 → 清理 | 状态 → 终态 / 回收资源 | "对端可能崩溃 / 会话已死" |
| **keepalive / 探测** | 周期性发送探测 | 发送探测、等待应答 | "维持中间设备映射 / 探测对端活性" |
| **重排定时器（reordering）** | 收到乱序报文 → 等待 | 不推进状态，延迟交付 | "乱序是可能的，先等待排序" |

**定时器设计的边界条件**：
- **定时器值**：过小 → 误判重传（放大负载）；过大 → 延迟感知失败。实际协议按 RTT 估计自适应（TCP 的 RTO = SRTT + 4·RTTVAR，见 TCP 模块）；
- **定时器与状态的一致性**：进入 `WAIT_REPLY` 时必须启动定时器，离开时必须停止。**定时器泄漏（忘了停止）** 是最常见 bug，会让已 DONE 的连接持续重传；
- **定时器与事件顺序**：定时器到期事件与报文到达事件可能同时发生，状态机必须定义优先级（先处理校验 / 去重，再处理超时），避免两个事件竞态导致状态分裂。

## 5. 正常 / 异常时序

- **正常时序**：状态沿 `初始 → 推进 → 终态` 前进，每个事件都被合法转移接收（§3.5）。
- **异常时序**：
  - **非法报文**：校验失败 / 类型非法 / 版本未知 → 丢弃（自转移或按协议定义）；
  - **乱序 / 重复**：由序号 / req-id 去重，不推进状态；
  - **对端沉默**：定时器重传，达到上限 → 失败态；
  - **对端异常**：NACK / 显式拒绝 → 失败态（明确失败优于无限等待）；
  - **状态分裂**：双方因定时器值不一致 / 非法报文处置不对称导致状态不一致 → 通常以连接重置 / 会话失败收尾（协议必须能从这个不一致中恢复或终止）。

## 6. 处理流程（无显式状态机时）

并非所有协议都有显式 `enum` 状态。无显式状态机时，用"隐式状态"分析（§1.2）：

- **滑动窗口 / 序号合法性**（TCP、QUIC）：状态由 `SND.UNA..SND.NXT`、`RCV.NXT` 等连续值隐含，合法性是区间判断而非离散枚举；
- **校验分层的协议**（以太帧、IP）：无连接状态，但"合法报文"由长度字段 + 校验决定——处理流程即"解析 → 校验 → 路由到上层"；
- **纯请求-响应**（HTTP/1.1 单请求）：状态退化为"请求中 / 响应中 / 空闲"，仍可用状态机描述。

分析无显式状态机的协议时，把"处理流程"画成状态机（每个流程阶段 = 状态），再标注其隐式状态变量（序号、窗口）。这样做的价值在于：能显式看到"未定义组合"与"定时器事件"，比平铺流程更能暴露错误路径。

## 7. 与 protocol.md 的连接

- **校验失败 → 丢弃**（protocol.md §3.5 / §6）在这里落地为"自转移（不推进状态）"；
- **长度 / 类型边界**（protocol.md §3.3/3.4）是事件合法性判断的输入：`recv(OTHER)` 正是"解析失败 / 类型非法"事件的汇聚；
- **错误模型**（protocol.md §4.4）在这里落地为具体的转移目标（丢弃 / 重传 / 失败）；
- **版本协商**（protocol.md §3.6）表现为状态机中"协商中"的过渡状态（如 TLS handshake 的版本协商阶段、QUIC 的 version negotiation 阶段）。
